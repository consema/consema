# plist 0.10.0 performance baseline

## Environment

- Date: 2026-08-07 (local)
- Windows 11 Pro 10.0.26200, x86-64
- Rust 1.97.1 stable (`8bab26f4f 2026-07-14`), LLVM 22.1.6, `--release` profile,
  `cargo run --locked --offline --release -p consema-conformance --example plist_baseline -- <iterations>`
- Commit: 0.10.0 development workspace (unreleased, HEAD `a447ce6`)
- CPU: 13th Gen Intel Core i9-13900HX, 32 logical processors; no CPU affinity,
  isolation, or background-process suppression

## Corpus and operations

Both inputs are repository-authored production-shaped fixtures. The XML corpus
is a preference-style plist embedded in the harness (`plist_baseline.rs`,
`PREFERENCE_XML`); the binary corpus is its byte-for-byte pinned `bplist00`
equivalent (`PREFERENCE_BINARY_HEX`), and the harness asserts both form
Complete documents at startup, so the baseline never runs on a broken corpus:

- `preference-plist.xml` (448 bytes), SHA-256
  `d3c68a659d139103525c6621068ae29f6c8cd70a3591a045171eccea21e959ba`:
  DOCTYPE, dict/array/string/integer/boolean, five keys with literal values.
- `preference.bplist` (142 bytes), SHA-256
  `8a049e230748a1be7017710de864d307cbd44bbe55d0073b1fafba2af317c4b9`:
  the pinned binary equivalent, object table + offset table + trailer.

Operations measured per iteration:

1. **parse** — `plist.xml@1` / `plist.binary@1` formation under default
   limits;
2. **projection** — exact `plist.value-tree@1` record projection;
3. **materialization** — canonical `plist.xml-canonical@1` /
   `plist.binary-canonical@1` including the mandatory reparse closure
   verification, returning no Document on any mismatch.

Recovery and adversarial-size behavior are covered by the hardening suites
(`consema-rs/consema-conformance/tests/plist_hardening.rs`；拆分前布局为 `crates/consema-conformance/tests/plist_hardening.rs`), not by this
wall-clock baseline.

## Results (5,000 iterations, 3 samples)

| Operation | Sample 1 ns/op | Sample 2 ns/op | Sample 3 ns/op | Median ns/op |
|---|---:|---:|---:|---:|
| parse plist.xml (448 B) | 73,206.2 | 65,942.8 | 67,693.4 | 67,693.4 |
| parse plist.binary (142 B) | 4,403.4 | 4,537.4 | 4,379.0 | 4,403.4 |
| projection value-tree | 6,855.4 | 6,973.8 | 7,529.6 | 6,973.8 |
| materialization xml-canonical | 81,683.4 | 84,023.8 | 82,904.0 | 82,904.0 |
| materialization binary-canonical | 13,062.6 | 13,255.6 | 15,271.0 | 13,255.6 |

The binary form parses and materializes faster than the XML form on the same
value model: the XML pipeline pays tokenization and decoded-text accounting,
while binary formation is direct byte-table consumption. Materialization
dominates both representations because the contract reparses the exact
generated bytes and compares the native value tree against the promised input
semantics before publishing; the cost is the price of the closure guarantee.
The parser is debug-safety instrumented and deliberately favors bounded
allocations over speed; the baseline is a reproducibility gate, not an
optimization claim.

The complete sample spread is retained deliberately. Future comparisons must
use the same corpus, operation definitions, release profile, and iteration
count. Results from another machine or toolchain must be reported separately
instead of being merged into this baseline.

## Reproducibility

```text
cargo run --locked --offline --release -p consema-conformance --example plist_baseline -- 5000
```

The harness ends with the closure contract assertions: both pinned records
materialize with `MaterializationFidelity::Exact` under their canonical
styles, so the baseline never runs on a corpus whose closure contract is
broken.
