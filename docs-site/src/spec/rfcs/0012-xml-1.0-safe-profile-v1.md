# RFC 0012: XML 1.0 safe Profile v1

- Status: Implemented in Consema 0.9.0
- Date: 2026-08-05
- Scope: a namespace-aware, side-effect-free XML 1.0 Profile; UTF-8/UTF-16
  source facts; lossless document and native tree semantics; bounded internal
  text entities; query, exact XML-tree projection, materialization, structural
  edit, recovery, security, and conformance boundaries
- Normative syntax: [XML 1.0 Fifth Edition](https://www.w3.org/TR/xml/)
- Normative namespaces: [Namespaces in XML 1.0 Third Edition](https://www.w3.org/TR/xml-names/)
- Upstream evidence: [W3C XML Conformance Test Suites](https://www.w3.org/XML/Test/)

## 1. Decision

Consema 0.9.0 publishes exactly one XML Profile:

```text
xml.1.0-safe@1
```

It is an XML 1.0 well-formed document Profile with mandatory namespace-aware
semantics and a deliberately smaller DTD/entity surface. It is not XML 1.1,
HTML, a validating processor, an XInclude processor, an XML Catalog client, an
XPath/XSLT engine, or a general resource resolver.

The Profile is selected before formation. A `.xml` extension does not authorize
external I/O, schema lookup, DTD validation, or application-specific mapping.
The parser consumes one complete document entity supplied as bytes and never
opens another entity, file, URI, network connection, registry, classpath, or
catalog.

The following layers remain separate:

```text
raw XML source and exact encoding facts
  -> lossless lexical pieces and reference spelling
  -> namespace-aware native document tree
  -> explicit XML-tree or PortableValue projection
  -> application schema/evaluation outside the Document
```

An XML element is not a JSON Object. Attributes and child elements are not one
map, mixed content is not whitespace to discard, and namespace prefixes are not
expanded names.

## 2. Source and encoding

Every entry point constructs a bounded `SourceSnapshot` before XML tokenization.
Unmodified rendering returns the exact original bytes, including a BOM,
declaration spelling, quote choices, line endings, references, and trivia. All
public spans remain half-open raw-byte ranges. Decoded UTF-8/scalar/UTF-16
locations are derived from the frozen source index and never replace raw spans.

V1 admits these document-entity encodings:

| Encoding | BOM | XML declaration |
|---|---|---|
| UTF-8 | optional | absent or case-insensitive `UTF-8` |
| UTF-16LE | required | absent, `UTF-16`, or `UTF-16LE` |
| UTF-16BE | required | absent, `UTF-16`, or `UTF-16BE` |

No-BOM source defaults to UTF-8. An explicit caller choice is evidence, not
permission to contradict a BOM or declaration. UTF-16 without a BOM is rejected
by this Profile even when a caller supplies endianness. UTF-32, Latin-1,
Windows code pages, EBCDIC, and other IANA encodings are explicit v1 Profile
exclusions; supporting them later requires a new Profile or source contract and
new conformance vectors.

The declaration, when present:

- is the first decoded construct after an optional BOM;
- uses version exactly `1.0`;
- contains only the XML grammar's `version`, optional `encoding`, and optional
  `standalone` pseudo-attributes in their required order;
- uses `standalone="yes" | "no"` when present;
- agrees with the selected source encoding under the table above.

The source layer retains complete BOM, declaration, caller override, selected
encoding, digest, and raw/decoded boundary facts. The tokenizer sees the
decoded document without treating the BOM as character data, while the
lossless syntax index still owns the BOM bytes.

XML end-of-line handling is semantic, not destructive. Raw CR, CRLF, and LF
spelling remains in source pieces; native character data follows XML 1.0 line
end normalization to LF.

## 3. Safe DTD and entity boundary

The Profile permits no DOCTYPE or an internal-only DOCTYPE with this bounded
subset:

- one root-name declaration matching the document element's QName;
- no external identifier;
- comments, processing instructions, whitespace, and internal general parsed
  entity declarations;
- an internal general entity value containing character data, character
  references, predefined entity references, or references to another admitted
  internal general entity;
- no `<` in replacement text and therefore no entity-generated markup.

The following constructs never trigger fallback behavior and make formation
Recovered with a stable security/profile diagnostic:

- a DOCTYPE `SYSTEM` or `PUBLIC` external subset;
- an external general entity, unparsed entity, notation, or `NDATA`;
- a parameter entity declaration or `%name;` reference;
- `ELEMENT`, `ATTLIST`, conditional-section, or validation declarations;
- an internal entity whose replacement text can create markup;
- an entity declaration or reference outside configured limits.

No callback exists through which parse can fetch excluded content. Recovered
syntax remains inspectable, but projection, document materialization, and edit
commit require a Complete Document.

The five predefined entities are always available with their XML meanings:

```text
lt -> <    gt -> >    amp -> &    apos -> '    quot -> "
```

Internal general entity names are unique. A declaration cannot override a
predefined entity. References are resolved deterministically after all admitted
declarations have been collected. Unknown references, recursion, indirect
cycles, invalid replacement characters, or a limit breach produce no partial
native text.

Expansion is guarded before and during allocation by declaration count,
reference count, reference depth, replacement bytes/scalars, total expanded
bytes/scalars, and amplification ratio. Limits apply across the whole document,
not independently per reference.

## 4. Formation and recovery

Formation continues to use:

```text
Complete
Recovered
FatalFormationFailure
```

`Complete` requires:

- a complete legal XML 1.0 document entity under the source rules;
- exactly one document element;
- matched, properly nested start/end tags;
- legal XML characters, names, comments, CDATA, PI, references, and declaration;
- namespace constraints and expanded name attribute uniqueness;
- an admitted and fully resolved DTD/entity subset, when present;
- exhaustive source coverage and every configured limit.

`Recovered` retains the immutable source, exhaustive token/trivia/error-region
coverage, ordered diagnostics, and every independently proven construct. The
parser may recover only at deterministic markup boundaries. It never invents a
closing tag, namespace binding, attribute value, entity replacement, or second
root to fabricate a Complete tree.

Invalid byte decoding, impossible source coordinates, allocation/host-size
overflow, or inability to construct exhaustive coverage is fatal. Syntax,
well-formedness, namespace, safe-DTD, and entity errors may form Recovered only
when the complete source can still be covered without asserting unproven native
semantics.

Projection, materialization from a Document, and edit commit require Complete.
Native and syntax queries may inspect proven parts of a Recovered Document and
can explicitly select error regions.

## 5. Namespace-aware native model

Snapshot-bound native roles are:

```text
XmlDocument
XmlDeclaration
XmlDoctype
XmlElement
XmlAttribute
XmlNamespaceBinding
XmlText
XmlCdata
XmlComment
XmlProcessingInstruction
XmlEntityReference
XmlErrorRegion
XmlSyntaxPiece
```

The immutable Document retains prolog order, one document element, epilog
order, and every exact source span. The document element owns an ordered child
content sequence. Child items are Element, Text, Cdata, Comment, or
ProcessingInstruction; they are never sorted or grouped by type.

One lexical QName retains:

```text
original prefix (optional)
local name
complete QName span
prefix span (optional)
local-name span
resolved expanded name = { namespace URI or none, local name }
```

Prefix spelling is source representation. Expanded-name equality compares the
namespace URI and local name, never the prefix. Namespace declarations are
ordered native associations with independent identity and source spans; they
are not ordinary attributes.

Namespace resolution follows Namespaces 1.0 Third Edition:

- the default namespace applies to element names, not unprefixed attributes;
- prefixed element and attribute names require an in-scope binding;
- `xml` is permanently bound to its standard URI;
- `xmlns` is reserved for namespace declarations and cannot be rebound;
- an ordinary name cannot use the `xmlns` prefix;
- namespace-name comparison is exact string comparison with no URI fetch or
  normalization;
- attributes on one element are unique by expanded name, not merely lexical
  QName;
- namespace scope is immutable ancestry-derived data, not a global mutable map.

An `XmlAttribute` remains an ordered association owned by exactly one element.
It retains QName/expanded name, quote style, raw value fragments, normalized
semantic value, and provenance. It is not a child node and is not merged with
namespace declarations.

## 6. Text, CDATA, and reference facts

Text and attribute values retain ordered fragments:

```text
Literal
CharacterReference
PredefinedEntityReference
GeneralEntityReference
```

Every reference has its own `NodeRef`, raw span, source spelling, resolved
string, and declaration provenance when applicable. Decimal and hexadecimal
character-reference spellings remain distinct source facts; both resolve only
to legal XML 1.0 characters.

Native Text semantic content is the concatenation of resolved fragments after
XML line-end normalization. CDATA remains a distinct child occurrence even
though its semantic characters can equal Text. Adjacent Text occurrences are
not automatically merged across CDATA, comments, PI, or entity-reference source
boundaries.

Attribute values use the XML 1.0 CDATA normalization rule because this Profile
does not process `ATTLIST` declarations. Whitespace normalization, reference
resolution, raw spelling, quote style, and provenance remain separately
observable.

Comments cannot contain `--` or end in `-`. A PI target cannot compare
case-insensitively equal to `xml`. CDATA cannot contain `]]>`. None of comment,
PI, or CDATA content is entity-expanded.

## 7. Lossless syntax coverage

Every non-empty raw byte belongs to exactly one ordered structural piece with a
format-owned syntax kind. The v1 kind set covers at least:

```text
Bom, Whitespace, LineBreak,
DeclarationOpen, DeclarationName, DeclarationValue, DeclarationClose,
DoctypeOpen, DoctypeName, DtdMarkup, DoctypeClose,
TagOpen, TagClose, EmptyElementClose, EndTagOpen,
Prefix, LocalName, Colon,
AttributeName, Equals, Quote, AttributeValue,
NamespaceDeclaration,
Text, EntityReference, CharacterReference,
CdataOpen, CdataText, CdataClose,
CommentOpen, CommentText, CommentClose,
ProcessingInstructionOpen, ProcessingInstructionTarget,
ProcessingInstructionContent, ProcessingInstructionClose,
ErrorRegion
```

Format kinds align one-to-one with the common `LosslessStructuralIndex` pieces.
Decoded tokenizer spans are converted back to exact raw-byte spans through the
source index; UTF-16 pieces therefore cover original code units rather than a
temporary UTF-8 buffer.

## 8. Query contracts

The native domain is:

```text
xml.native-semantic-query@1
```

It supports document/prolog/root/epilog navigation; child and descendant
elements; ordered content; attributes; namespace declarations and in-scope
bindings; text/CDATA/comment/PI; references; owner/parent navigation; and
filters for QName prefix/local, expanded namespace/local, node kind, attribute
value, PI target, and reference kind/name.

The lossless domain is:

```text
xml.lossless-syntax-query@1
```

It supports syntax-kind/text filtering, exact source order, selection,
`core.take@1`, `core.distinct-by-identity@1`, limits, cancellation, and explicit
Completed/Cancelled/Failed terminal states.

Native order is document order. Element attributes and namespace declarations
preserve their respective source orders; child content preserves mixed-content
order. Descendant traversal is bounded pre-order. No query resolves a URI,
evaluates XPath, loads a schema, or expands application data.

## 9. Projection

The exact default XML target is:

```text
xml.projection.element-tree@1
```

It produces a versioned `xml.element-tree@1` PortableValue record containing
declaration facts, admitted internal entity declarations, one namespace-aware
root, ordered namespace declarations, ordered attributes, ordered mixed
content, exact text/reference fragments, CDATA, comments, and PI. It is an XML
semantic tree contract, not a generic Object mapping and not a replacement for
lossless source syntax.

Additional explicit targets are:

```text
xml.projection.text-content@1
xml.projection.simple-entry-mapping@1
```

Text-content projection is always Transformed and requires a policy for
including descendant text and CDATA. It reports every discarded element,
attribute, comment, PI, and source-reference distinction.

Simple-entry-mapping projection is admitted only when the selected subtree has
no mixed content, comments, PI, duplicate expanded child names, non-text child
values, namespace collision, or attribute/child ambiguity under the requested
mapping. Attribute prefix, text key, repeated-child policy, expanded name key
encoding, and collision behavior are all explicit. The default for any omitted
policy is failure, not LastWins or convention guessing.

There is no `xml-to-json-default`, automatic attribute `@` prefix, automatic
text `#text` key, singular/plural heuristic, namespace stripping, or child
grouping. Any authorized transformation emits report events and provenance.

## 10. Materialization

The canonical style is:

```text
xml.safe-canonical-document@1
```

It consumes a fully validated `xml.element-tree@1` value and creates a new
`xml.1.0-safe@1` Document. It is not W3C Canonical XML and does not claim C14N
equivalence. The style deterministically chooses declaration spelling, quote
style, indentation, namespace declaration placement, empty-element spelling,
reference spelling, and LF/CRLF according to the request.

UTF-8, UTF-16LE, and UTF-16BE output are supported under the source rules.
UTF-16 output always carries its corresponding BOM. Requested encoding,
newline, output bytes, depth, node, attribute, namespace, entity, report, and
provenance limits are checked before publication.

Materialization validates the complete tree before allocating proportional
output, encodes it, reparses the exact generated bytes under the promised
Profile and encoding, and compares the reparsed native tree to the promised
input semantics. Failure returns no target Document or partial output.

## 11. Structural edit

V1 publishes these snapshot-bound operations:

```text
xml.edit.replace-text@1
xml.edit.insert-attribute@1
xml.edit.remove-attribute@1
xml.edit.rename-attribute@1
xml.edit.set-attribute-value@1
xml.edit.insert-element@1
xml.edit.remove-element@1
xml.edit.rename-element@1
```

Each operation targets one exact `NodeRef`. Placement uses one exact parent and
optional sibling/attribute anchor. Duplicate expanded attributes, invalid
namespace bindings, unbound prefixes, reserved-prefix misuse, ancestor/self
placement, stale snapshot, overlapping replacements, and operations that would
break mixed-content or document-root invariants fail before commit.

Semantic replacement accepts text or validated QName/expanded name facts, not
raw untrusted markup. New literal content is XML-escaped under the existing
encoding; exact entity/reference insertion is a future separate operation.

Commit preserves every byte outside operation-owned spans, reparses the target,
verifies promised XML/namespace semantics, produces a complete ChangeSet,
derives an `UntouchedByteProof`, and emits a replayable SourcePatch. Dry-run and
commit have identical replacement sets and target digest. No operation writes a
filesystem path.

## 12. Resource and failure contract

`XmlParseLimits` includes common source/node/piece/diagnostic limits plus:

- decoded bytes/scalars and nesting depth;
- element, attribute, namespace-declaration, and mixed-content item counts;
- QName/local/prefix/namespace URI and attribute-value lengths;
- comment, PI, CDATA, and text lengths;
- DTD bytes, entity declarations, references, expansion depth, expanded bytes
  and scalars, and amplification ratio;
- recovery regions.

Query, projection, materialization, edit, protocol, proof, and patch keep their
existing independent limits. Integer conversion and multiplication are checked
before allocation. Limit failures never masquerade as an empty tree, truncated
text, skipped attribute, shortened query, partial target, or successful edit.

Stable diagnostics distinguish source/declaration conflicts, lexical XML
errors, tree well-formedness, namespace errors, excluded DTD/entity constructs,
unknown/cyclic/over-limit entities, projection mapping failures,
materialization representability, edit ownership/conflict/reparse, and query
domain/role/limit failures.

The `xml.*` diagnostic codes are registered by this RFC and are part of the
`xml.1.0-safe@1` contract. They do not enter the `consema-protocol` core error
registry, which covers only core/protocol and line-format contract codes
(RFC 0011 §10). When XML diagnostics are externalized through the protocol,
they are handled through the registry's corresponding format section or per
RFC 0011's error-code classification rules.

## 13. Rust backend boundary

The Rust implementation pins `xmlparser 0.13.6` as a zero-allocation XML 1.0
token/span backend. It performs no I/O and forbids unsafe code. Consema owns and
tests every contract the backend does not provide:

- UTF-8/UTF-16 source resolution and raw-span mapping;
- declaration/profile enforcement;
- root and start/end tree validation;
- duplicate expanded-attribute rejection;
- namespace scope and expanded names;
- safe DTD subset and bounded entity expansion;
- XML line-end/attribute normalization;
- immutable native tree, recovery, diagnostics, query, projection,
  materialization, and edit.

No backend token, span, error, tree, or namespace type enters the public API.
Changing the backend cannot change a Profile, diagnostic, query order,
projection, generated bytes, or conformance result.

## 14. Conformance evidence

The 0.9.0 release gate requires:

- language-neutral cases for UTF-8/UTF-16, declaration, namespace scope,
  expanded names, attributes, mixed content, references, safe internal
  entities, recovery, query, projection, materialization, edit, and limits;
- exact counterexamples for default namespace on attributes, prefix rebinding,
  duplicate expanded attributes, mixed-content order, unknown/cyclic entities,
  external subset/entity denial, and XML-to-Object ambiguity;
- W3C XML/Namespaces suite inventory pinned by release identifier and digest;
- complete manifest accounting: applicable valid cases, applicable invalid
  cases, and explicit Profile exclusions for validation, external resources,
  XML 1.1, unsupported encodings, or excluded DTD constructs;
- an encoding corpus covering BOM/declaration conflicts, UTF-16LE/BE, non-BMP
  names/content, invalid sequences, and raw/decoded span closure;
- production-shaped Maven, Spring, logging, application-server, and generic
  namespaced configuration fixtures without secrets or unclear licenses;
- mutation, truncation, nesting, namespace, entity-amplification, long-value,
  count, output, and protocol adversarial gates;
- current Rust and MSRV tests/Clippy, rustfmt, rustdoc, dependency audit,
  package extraction, and a fixed performance baseline.

An upstream case is never silently ignored. An exclusion records the suite case
identity, exact excluded Profile rule, and why accepting it would require I/O,
validation, a different XML version/encoding, or a broader DTD contract.

## 15. Non-goals

Consema 0.9.0 XML support does not provide:

- XML 1.1, namespaces 1.1, schema, DTD validation, Relax NG, Schematron, XPath,
  XQuery, XSLT, XInclude, canonical XML, signatures, or encryption;
- external subsets/entities, parameter entities, unparsed entities, notation,
  catalogs, URL/file/classpath resolution, or user-supplied resolver callbacks;
- DOM mutation, in-place mutable nodes, application object serialization, or
  automatic XML-to-JSON conventions;
- XML Properties table semantics or plist value semantics merely because those
  vocabularies use XML syntax;
- formatting an existing source document, semantic diff/merge, incremental
  parse, filesystem transactions, stable process plugins, or Go.

## 16. Rejected alternatives

- **Deserialize XML directly to maps:** rejected because it loses attribute
  ownership, namespace bindings, repeated children, mixed content, comments,
  PI, CDATA, references, and source identity.
- **Disable namespaces for compatibility:** rejected because the same Profile
  would then assign contradictory expanded names.
- **Use prefix as namespace identity:** rejected because prefixes are scoped
  source spelling and can be rebound.
- **Let a backend fetch entities:** rejected because parsing would perform
  hidden I/O and become environment/time dependent.
- **Reject every entity reference:** rejected because predefined, character,
  and bounded internal text entities are common, deterministic XML content.
- **Implement a full DTD processor:** rejected for the safe v1 configuration
  boundary; validation and parameter/external entity machinery materially
  enlarge the attack and I/O surface.
- **Call generated output C14N:** rejected because this Profile's deterministic
  style serves new-document materialization and does not implement the W3C
  Canonical XML algorithms.
